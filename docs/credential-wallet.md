# Project credential wallet

An organisation administrator or security lead can manage one credential connection per provider in each project. Developers assigned to a project can view connection metadata and add a connection for a provider that does not already have one. Existing connections can only be replaced, reverified or removed by an administrator or security lead. All connections are shared by the project; add only credentials you are authorized to use for that purpose. Credentials are encrypted using AES-256-GCM with a fresh nonce and the `WALLET_ENCRYPTION_KEY` environment variable; the API only returns connection metadata and verification status. The key is a 32-byte hexadecimal value. Back it up securely: changing or losing it prevents decryption of existing connections. Set it using a secret manager on a deployed host.

For incidents assigned to a project, the pipeline uses that project's verified wallet connection for the matching provider on both initial collection and refresh. A missing, pending, failed or unreadable connection produces a collection error; it never falls back to a global reader or another project's wallet. Save or reverify the connection and refresh the incident. Replacing or removing a connection affects future collections. Legacy incidents without a project use backend environment configuration for other providers; AWS collection requires a project wallet.

For AWS, the wallet form requires only the reader access key ID, secret access key and region. The region is used for STS verification and CloudTrail management-event lookup. An administrator or security lead can configure additional regions and an S3 trail source under **CloudTrail collection settings** on an AWS incident timeline. These settings are stored with the encrypted project wallet reader; the settings API never returns the credentials. When the same reader is saved again through the wallet form, its existing settings are preserved; replacing it with a different reader does not carry them over. CloudTrail LookupEvents does not include S3 object data events. Trail-file collection needs an evidence bucket and narrow prefix, S3 ListBucket and GetObject permissions, and any necessary KMS decrypt permission. Trail data events must already be enabled and delivered by AWS. The collector filters records by exact access-key ID and collection window, deduplicates event IDs and retains the object path and a SHA-256 hash of the compressed file. This hash is not AWS digest validation.

Collection uses an independent wallet reader, distinct from the exposed key. It accepts a maximum 90-day window and limits a collection to 100,000 events, 2,000 pages per source, 1,000 gzip files per prefix, 16 MiB compressed and 64 MiB decompressed per file. A malformed, inaccessible or oversized file, a repeated pagination token or an exceeded limit causes collection to fail rather than silently reporting incomplete evidence. Use a narrower prefix when necessary. STS verification does not check these S3 permissions. CloudTrail delivery delays can require a later refresh.

The AWS incident timeline summarizes stored management, data and unspecified event categories and the number of records supplied or referenced in an import. It also shows whether an S3 trail source is configured in the current verified wallet. These describe the records and current settings only; they do not show whether past collection used the current settings or whether CloudTrail logged every request.

For evidence already downloaded from CloudShell, an administrator or security lead can open the AWS incident and use **Import CloudTrail evidence**. Preview a CloudTrail `Records` JSON file, a LookupEvents `Events` JSON response, or either format compressed as `.json.gz`; matching uses the incident's exact access-key ID from the CloudTrail record. For LookupEvents, the embedded `CloudTrailEvent` must be present and event IDs and names must not conflict with the outer response. Matching records without an event ID are rejected, while records without a key ID or with a different key are excluded and counted in the preview. A LookupEvents `NextToken` indicates more pages and is shown as a warning. Imported records persist through later refreshes, are classified using the existing rules, and update the deterministic report. Imports are labelled user-supplied: neither the SHA-256 hash nor the import establishes the file's AWS origin. JSON and gzip uploads are limited to 16 MiB compressed, 64 MiB decompressed and 100,000 records. Normalized files, ground truth and ZIP archives are not supported by this import yet.

AWS incident details group a successful S3 read and copy only as a likely relationship when the source object, access-key ID and source IP match within three seconds and both records have exactly one candidate. Every original record remains in the timeline. This is not proof that a read was caused by a copy, and ambiguous records remain ungrouped. The AWS repeated-access rule excludes likely copy-associated reads from its threshold; ambiguous reads are still counted as records. Repeated successful reads receive a higher severity but remain classified as data access. A copy is data access, not proof of exfiltration. Failed AWS requests remain visible as attempts and are excluded from completed-impact severity and financial estimates. An incident with only failed AWS requests after exposure has unknown completed-impact severity.

An incident refresh keeps the previous events and report while collection is pending and if collection or event persistence fails. The incident shows an error when the refresh fails; the retained report describes the previous successful collection. A successful refresh replaces the collected events, including when the new query returns no events, so provider retention and time-range limits still matter.

Choose a reader authorized for the affected provider account and scope. Stripe readers must match the key's test/live mode and the operator must confirm the account; the application cannot independently infer account ownership from a masked key. Twilio association requires an Account SID matching the wallet reader. Azure Activity Log is scoped to the reader's subscription and the separately associated application identity. Verification does not establish ownership of an exposed credential or guarantee that all collection permissions are available.

## Verification

Saving a connection starts an in-process background check. A verified status confirms only the particular operation below; it does not establish every permission required for forensics, nor does it prove that the connection belongs to the account of an exposed key.

- AWS: STS GetCallerIdentity. This checks authentication and does not confirm CloudTrail read permission.
- Google Cloud: request up to one Cloud Audit Logs entry in the service account's project. The service account JSON must include `project_id`.
- Azure: request Activity Log events from the configured subscription. Enter the application (client) ID, not the service principal object ID, and use a matching client secret value, not its key ID. The check does not prove that the reader belongs to an exposed credential's application.
- Stripe: list up to one event using a secret or restricted test or live key with Events read permission. Use a restricted key where possible. Balance permission is not required.
- Twilio: list up to one message using the owning Account SID and either an API key SID and secret or the account Auth Token. This does not establish Calls or Monitor Events access. Service and Environment SIDs identify Serverless resources and cannot authenticate a reader.

Verification errors shown in BreachTrace are intentionally generic to avoid disclosing provider responses or credentials. Recheck credentials, network access and permissions with the provider if a check fails. Checks occur in the backend process: if it stops mid-check, a pending connection can be manually verified again after restart.

## Keyless GCP reader impersonation

An administrator or security lead can select **Google Cloud → Keyless reader impersonation** and enter the target GCP project ID and independent reader service-account email. The backend obtains source Application Default Credentials (ADC) and impersonates that reader with the Logging read scope; it does not fall back to querying logs as the source identity if impersonation fails. Developers cannot create this connection. Existing service-account JSON connections continue to work.

Alternatively, an administrator or security lead may paste or upload an independent source service-account JSON in the same wallet form. It is encrypted with the other wallet values, is never returned by the API, and is used only to impersonate the configured reader. The source must have Token Creator permission on that reader. Neither the source nor the reader should be the identity under investigation; the collector rejects a matching configured source or reader. This option requires an existing authorized source key and does not create keys or bypass organization policy. Leave it empty to use backend ADC instead.

The backend process needs an independently authenticated ADC source identity with `roles/iam.serviceAccountTokenCreator` on the designated reader, and the IAM Service Account Credentials API must be available. Grant the reader the necessary Cloud Logging access, including `roles/logging.privateLogViewer` for Data Access logs in the default bucket where appropriate. Use the target identity's email, not the experiment or exposed credential. ADC is resolved on the machine running the backend: Cloud Shell credentials do not automatically exist on a different Mac or in a container. Configure local ADC for an authorized source identity before starting the backend; see [Google's impersonation guide](https://docs.cloud.google.com/docs/authentication/use-service-account-impersonation). A successful wallet check only confirms the specific Cloud Logging list operation, not completeness of historical records.

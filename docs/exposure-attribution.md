# Exposure lifecycle and attribution scope

This document records the current scope and the decisions for improving it. A detected credential, an observed provider event, and evidence that a particular key caused an action are different facts.

## Exposure lifecycle

- **Start:** A webhook incident uses the triggering commit timestamp as an estimated start. It does not prove the repository was public then or that the credential had not appeared elsewhere earlier. A snapshot scan has no known exposure start. An explicitly added snapshot finding is a detection-only incident whose stored timestamp represents snapshot observation, not first exposure.
- **Collection:** Collectors request up to 30 days of recent provider history through collection time, subject to provider retention, permissions, pagination and logging. Earlier records are context; scoring uses events at or after the estimated start. This is a collection interval, not a confirmed exposure window.
- **End:** Ordinary incidents do not automatically establish a rotation or revocation time. A recorded `exposure_end` has no source/provenance field, and must not be presented as independently confirmed provider revocation. Experiment-specific monitors exist for configured test credentials; they do not establish general coverage.
- **Observations:** Administrators and security leads can record a lifecycle observation with its source, observation time, confidence, masked credential hint, recording user and record time. These are explicitly operator-reported, including revocation and rotation; they do not prove provider verification, change the exposure end, or exclude later events. Other project members can view them. Do not include secrets in the source.
- **Decision:** Keep closure unknown unless evidence is available. A future provider integration should distinguish provider-confirmed revocation from an operator assertion, expiration, denial, timeout, network error or missing permission, and support late-arriving logs. Do not use a timeout or a failed authentication alone as proof of rotation. Updating or deleting repository content does not revoke a credential.

## Current provider attribution and feasible improvements

| Provider | Current BreachTrace scope | Possible improvement and boundary |
| --- | --- | --- |
| AWS | CloudTrail lookup by detected access key ID, for events available through the configured reader and region. | An event's `userIdentity.accessKeyId` can identify the signing key, but the field can be absent and temporary credentials have their own IDs. Broader trails/data events and session correlation would need additional collection and evidence checks. See [AWS identity fields](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-user-identity.html). |
| Google Cloud / Firebase | Cloud Audit Logs are matched by service-account email; a shared service account can have multiple keys. | Administrators or security leads may associate a key ID they have independently identified with the incident. Where `authenticationInfo.serviceAccountKeyName` and the principal both match, the timeline labels the event as matching the operator-associated key; a different key is labelled separately, and missing or inconsistent fields remain inconclusive. The association is an operator assertion, not independent proof that this key was leaked. Some services omit the field; impersonation and incomplete logs remain limitations. See [Google Cloud audit examples](https://docs.cloud.google.com/iam/docs/audit-logging/examples-service-accounts) and [service-account key guidance](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys). |
| Azure | Activity Log is matched to application/caller identity within the reader subscription. Different secrets for the same application can show the same activity. | An admin or security lead can separately query Microsoft Graph beta service-principal sign-ins using the project reader, with an optional operator-supplied credential key ID. Records may contain `servicePrincipalCredentialKeyId`; matching identifies authentication evidence, not the credential used for every later Activity Log operation. The query requires Graph `AuditLog.Read.All` application permission with admin consent, appropriate licensing and available logs; results are temporary and capped. No automatic session join is performed. See [Graph signIn](https://learn.microsoft.com/en-us/graph/api/resources/signin?view=graph-rest-beta), [permissions](https://learn.microsoft.com/en-us/graph/api/signin-list?view=graph-rest-beta), and [sign-in log fields](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/aadserviceprincipalsigninlogs). |
| Stripe | Events API records account-level state changes; the optional sandbox CLI stream captures new request metadata while running. Neither current path identifies the key responsible for each record, and Events does not include read-only requests. | Stripe's Dashboard offers [Workbench request logs for a key](https://docs.stripe.com/keys#view-api-request-logs-for-a-key). That UI capability is not currently integrated into BreachTrace. Do not claim that the existing Events API or CLI stream supplies equivalent per-key historical logs. |
| Twilio | Messages, calls and supported Monitor Events are collected at account scope. | Monitor Events document account/user actor identifiers where available, but the current resources do not establish which `SK` key made each request. Future provider sources should be evaluated record by record; account membership, time and source IP alone are not proof of exact-key use. See [Twilio Monitor Events](https://www.twilio.com/docs/usage/monitor-events). |

## Interpretation rules

Label events by the strongest supported identity: exact key when established, otherwise principal/application or account. Do not infer malicious intent solely from a timestamp or an account match. An empty timeline does not prove that the credential was unused. Provider log retention and configuration constrain all results.

The current deterministic report and PDF explain the uncertainty for newly generated reports. Previously stored reports and previously indexed knowledge passages may retain older wording until refreshed and re-indexed; users should use the current timeline and this document when reviewing them.

## Repeated Azure secret detections

For new webhook detections, BreachTrace computes a project-scoped keyed fingerprint of an Azure client secret and records each distinct commit against one incident. A replay of the same commit is not a new occurrence. The secret itself is not stored for this feature. An incident and dashboard warning appear after another distinct commit. The initial commit remains the exposure-start estimate; each later commit is a separate occurrence, not an independently confirmed exposure interval. Existing incidents from before fingerprinting cannot be safely matched from masked hints, so the first new occurrence of an older secret starts a new tracked incident. Preserve the wallet encryption key: changing it prevents matching future occurrences against earlier fingerprints. This feature currently covers Azure client-secret webhook detections only.

For Azure, Activity Log records application activity and cannot separate client secrets. The on-demand Graph sign-in query can compare a user-supplied credential key ID to sign-in records, with the stated API permissions and provider coverage; matching sign-ins do not establish which subsequent resource operations were performed with that credential. The query reports matched sign-ins in the original estimated exposure window and does not yet provide separate assessments for later commits.

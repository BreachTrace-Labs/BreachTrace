# Novelty and literature review

**Selection.** The question worth pursuing is whether a responder can tell which conclusions about a *particular exposed credential* survive when ordinary activity by another credential is interleaved with it. The closest competitors already correlate events, investigate identities, summarize incidents and normalize audit data. An empirical comparison must include a competent provider-native investigator who can inspect the same fields.

## Review method and access

Targeted review through 19 November 2026. Starting points were the deck and repository dossier. Searches combined exposed GitHub credentials, benchmark, remediation, cloud forensic reconstruction, provenance, multi-tenant logging, audit investigation, incident summaries, non-human identity governance and key usage. Included primary research with identifiable evaluation settings, original industry measurements, standards and first-party capability documentation. Press coverage, unverifiable deck assertions, and secondary summaries were excluded. This is a scoped search, not a systematic review or proof of priority. Paper pages/abstracts and accessible text are distinguished below. Published metrics belong to their respective data and cannot be pooled with BreachTrace measurements.

## Three paper narratives

| Candidate title | Argument, required evidence and decision |
|---|---|
| *Which Key Was Used? Measuring Attribution Limits After Repository Credential Exposure* | Primary. Measure how much attribution survives acquisition, normalization, scoring and prose. Compete with provider-native field queries. Require paired mixed identities, independent action truth, raw-to-report audit and real-source replication. Risk: a trivial key-equality check explains all gains. If so, publish measured limits and equivalence, not a new matching algorithm. Digital forensics or security measurement. |
| *When Does a Secret Scanner Miss an Occurrence?* | Secondary standalone possibility. Compare occurrence versus unique-credential scoring on independently reviewed repositories with repeat occurrences. Existing CredData misses motivate the question. Gitleaks/TruffleHog, SecretBench and prior comparative work set a high bar. Needs a representative, held-out corpus, path parity and independent spans. Empirical software engineering or mining repositories. |
| *Do Forensic Summaries Preserve Credential Uncertainty?* | Optional separate paper. Compare template, raw-log model, facts-only model and validated hybrid on ambiguity-rich cases with blinded reviewers. Kramer and AuditBench narrow the gap to preserving identity/outcome scope. Strong feasibility for controlled replay, weak basis for productivity claims without analysts. Usable security or applied incident response. |

## Contribution decisions

1. **Tier 1 / C1.** A matched action–record–assertion benchmark separating actual use, source observability, recoverability and downstream assertion scope. Existing historical evaluator supplies record joins. New data and independent truth required. A fair raw-field reference recovering everything available would validate the reference and reveal the ceiling.
2. **Tier 1 / C2.** Empirical characterization of wrong-key assertions versus useful exact-key coverage across evidence sources and output surfaces. Compare current behavior with explicit field-aware reference, principal/time join and abstain-all. The metric pair prevents winning by silence. A null comparison with a native query restricts novelty to cross-surface measurement.
3. **Tier 2 / C3.** Temporal, outcome and normalization errors as mechanisms explaining C1/C2. Record grouping, denied operations, timestamp boundaries and missing fields are controlled ablations. Publish failures as well as preservation. Latency and resource cost characterize feasibility.
4. **Tier 2 / C4.** Claim-level report fidelity where a template/LLM is used. Only advance to a standalone claim with blinded independent labels and a matched generation budget.
5. **Tier 3.** Incident priority ranking, source onboarding, held-out provider transfer, real analyst decision time, detector-span replication and longer operational monitoring. Each needs new labels, workload or participants. Independent axes include coverage per additional evidence source, harm of false reassurance, and benefit of abstention under a finite review budget.
6. **Tier 4.** Reject priority claims for unified APIs, LLM prose, large rule counts, the UI, secret validation, universal lifecycle tracking, calibrated risk, true financial damage, legal compliance or attacker identity. Reject claimed savings or exploitation speed from demo timings. Privacy-preserving or tamper-proof forensics would require a different evaluation.

**Novelty review decision.** A technically competent reviewer can reproduce much of the application with existing scanners and native queries. The existing prototype by itself lacks enough demonstrated novelty for a strong security systems paper. The unresolved empirical question in the sources reviewed is whether an independently ground-truthed, mixed-key evaluation can quantify how much *recoverable* identity information survives all the way to the investigator. Before submission, forward/backward-search the closest papers and record query date, data sources, exclusions and any equivalent benchmark. If one exists, use it as the primary comparator and reposition the work as replication or extension.

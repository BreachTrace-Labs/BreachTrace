# Local models and research comparisons

BreachTrace can use two local Ollama models: one to write checked report prose and an optional second one to answer Search questions from retrieved passages. In **Settings → Model settings**, select **Local model via Ollama**, enter an installed report model and, optionally, an installed answer model. Leave the answer model blank to reuse the report model. The test button checks both selected Ollama models when they differ; also verify answer behavior with a grounded Search question. Selecting a model does not download it or establish its quality.

Enable **Offline model mode** to reject cloud model providers and require locally cached embedding files. If the embedding model is not cached, retrieval falls back to keyword search rather than downloading it. Ollama remains bound to loopback. This option applies to model inference and embedding downloads; GitHub and provider log integrations still use their networks. The current embedding model is configured at backend startup through `EMBED_MODEL` and `MODEL_CACHE_DIR`. Do not switch embedding models on an existing index without rebuilding its vectors: stored vectors currently lack model identity and dimensions may differ. A reranker and in-app embedding-model switching are not implemented.

## Compare installed report models

In **Research → Local report model comparison**, select up to four models already present in Ollama, select 1–12 synthetic cases and run the comparison. No model is downloaded and real incident data is not used. Results and the complete synthetic per-case record can be downloaded as JSON. The deterministic report template is included as a baseline. The benchmark records the model digest, fixture hash, prompt version, hardware, latency and validation/fact-coverage proxies. These proxies do not measure human-rated factual accuracy or retrieval/RAG-answer quality. Small samples do not support general model rankings. Results are stored in a database-backed job; the page displays the latest run. A comparison can take minutes, and concurrent model comparisons are intentionally restricted.

The fixed retrieval fixture can be evaluated separately with `PYTHONPATH=backend DATABASE_URL=sqlite:// EMBED_ENABLED=false .venv/bin/python -m rag.evaluate` for keyword-only retrieval; omit `EMBED_ENABLED=false` to evaluate the configured embedding model. This does not compare multiple embedding models in one run and is not a substitute for independent labels.

## Bring your own cloud key

Settings → Model settings also accepts OpenAI, Groq, Gemini and Anthropic/Claude. Select the provider, enter an exact model ID available to your account, enter its key, save, and test. Selecting a cloud provider switches offline-model mode off visibly. Keys are write-only and held in the backend process until restart; they are not saved to the preferences JSON or returned by APIs. Changing providers clears the entered in-memory key. No environment edits are needed to enter a key here. Cloud generation sends fact sheets or the question and retrieved passages to the selected provider and can incur charges. The incident question box enables answer generation by default and links directly to model settings; the checkbox can still be disabled for retrieval-only results.

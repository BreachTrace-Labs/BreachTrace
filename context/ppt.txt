
The Situation
Every day developers accidentally commit secrets — API keys, passwords,
tokens — to public GitHub repositories. Automated bots find these secrets
within minutes and start using them.
The Current Gap
Tools like GitGuardian already exist. They detect the leak and send an alert.
But they only answer: "Was your key leaked?"
Nobody answers the question that actually matters:
"What happened BECAUSE your key was leaked?"
Was my database accessed?
Was customer data stolen?
Were fake charges created?
Do I need to inform my users legally?
Today developers rotate the key and hope for the best. They never actually
know.
Why This Matters?
At scale: 39 million secrets were leaked on GitHub in 2024 alone. The
average cost of a breach involving compromised credentials is $4.88
million (IBM Cost of Data Breach Report 2024). Automated bots exploit
leaked credentials within 5 minutes of exposure.
In reality: In January 2024, a single GitHub token was accidentally
exposed. Before it was revoked, attackers used it to steal 270GB of
internal New York Times data including source code and infrastructure
tools. The token was exposed for minutes. The damage was permanent
and irreversible.
For compliance: GDPR, SOC2, and PCI-DSS all require organisations to
assess the impact of a credential exposure and report if personal data
was accessed. Without an automated forensic tool, this assessment is
either done manually over hours or skipped entirely — both of which

Problem Statement
No automated system exists that correlates a GitHub credential exposure event with audit logs across
affected cloud and SaaS platforms to determine what actions were taken during the exposure window,
classify the blast radius, and generate an actionable forensic impact report — leaving developers
blind to the actual damage caused by their leaked credentials.

Solution - BreachTrace
What BreachTrace Does
A universal credential forensics platform that automatically detects leaked secrets on GitHub and traces
their exploitation across every affected platform — delivering a complete forensic impact report in under
60 seconds. No manual investigation. No security expertise required.

Research Objective of the Project
Primary Research Objective: To design, implement, and
evaluate BreachTrace, a novel automated cybersecurity
framework that bridges the "Forensic Causality
Disconnect" between public source-code repositories
and multi-cloud infrastructure.
Specific Project Goals:
Unify and Normalize Telemetry: Develop a crossplatform data schema that autonomously links
credential exposure events (Point of Origin, e.g.,
GitHub, IaC files) directly to cloud infrastructure
API logs (Point of Exfiltration, e.g., AWS, GCP, Azure).
Establish Proof-of-Usage (PoU): Overcome the
false-positive limitations and alert fatigue of
current static AI/regex secret detectors (e.g.,
GitGuardian, CredDigger) by utilizing cloud audit
logs as a deterministic validation oracle to confirm
active exploitation.
Calculate Dynamic Blast Radius: Create a dynamic
risk assessment model that categorizes the impact
of a leaked credential based on its actual
"permissions-in-use" to accurately measure the
multi-step threat it poses.
Automate Closed-Loop Incident Response:
Generate actionable "Causal-Chain Forensic
Reports" for developers and integrate with SOAR
playbooks to auto-revoke compromised
credentials, drastically reducing the Mean Time To
Respond (MTTR) to mitigate the massive economic
impact of modern 72-minute breakout attacks


FUNCTIONAL REQUIREMENTS
FR1: Detect leaked credentials in public GitHub repositories via webhook within
30 seconds of commit and support 7 credential types (AWS Access Keys, GCP
Service Account Keys, GitHub Personal Access Tokens, Stripe Secret Keys, Twilio
Auth Tokens, Database Connection Strings, NPM Tokens)
FR2: Calculate exact exposure window from commit timestamp to credential
revocation timestamp and query audit logs across platforms — AWS CloudTrail,
GCP Cloud Audit Logs, Stripe Events API, GitHub Audit Log API, and Twilio Usage
Records API
FR3: Normalise audit log data from all platforms into a unified forensic event
schema and classify every event into one of seven impact categories
(Reconnaissance, Data Access, Data Exfiltration, Resource Abuse, Privilege
Escalation, Financial Abuse, Communication Abuse)
FR4: Compute overall incident severity score (Low, Medium, High, or Critical),
generate forensic timeline showing chronological sequence of events across
platforms, and display interactive D3.js timeline on dashboard
FR5: Generate plain English incident summary using Gemini API, create specific
remediation checklist based on detected impact categories, and automatically
flag GDPR, PCI-DSS, and SOC2 notification requirements based on data types
accessed
FR6: Display complete forensic report on web dashboard within 60 seconds of
detection, showing blast radius summary, affected resources, source IP
addresses, and financial impact estimate
FR7: Handle zero-activity reports (confirm nothing happened when no audit log
activity is detected) and support 250 controlled experimental exposures for
research dataset generation
NON FUNCTIONAL REQUIREMENTS
NFR1: Detection latency must be under 30 seconds from GitHub commit to
alert, and complete forensic report must be generated within 60 seconds of
detection
NFR2: System must run on a standard developer laptop with zero infrastructure
cost — all APIs must use free tiers only
NFR3: No raw credential values may be stored at any point — only metadata
and audit log results are allowed
NFR4: Dashboard must be usable by developers with no prior security
expertise, and system must handle API rate limits gracefully using exponential
backoff
NFR5: All forensic collectors must operate in parallel with graceful handling of
auto-revocation and unavailable platform APIs — partial reports are
acceptable
NFR6: All experiment data must be generated using throwaway accounts with
restricted permissions, and Stripe integration must use test mode exclusively
with no real financial transactions
NFR7: Research dataset must contain minimum 35 samples per credential type,
classification accuracy must exceed 90% on controlled test set, and system
must be deployable using Docker for consistent cross-platform execution

There are no pre-existing dataset exists for this problem.
Our aim is to generate the first cross-platform credential exploitation dataset through
controlled ethical experiments.
Generation Process
Create throwaway accounts on AWS, Stripe, GitHub, GCP, Twilio
Deliberately expose test credentials to public GitHub repositories
Simulate attacker behaviour from a second device — controlled API calls
BreachTrace automatically collects forensic data across all platforms
250 controlled exposures — 35+ per credential type
Why 250?
7 credential types requiring minimum 30 samples each for statistical significance
250 ÷ 7 = 35 samples per type — clears Welch t-test threshold comfortably
Each experiment cycle takes 10–15 minutes — 250 cycles feasible across 4 team
members in 4 weeks
Sufficient for both rule-based classifier validation and ML model evaluation
Research Value
First empirical dataset measuring:
Exploitation speed across 7 credential types
Blast radius severity distribution across 250 exposures
Exposure duration vs severity correlation
Ethical Advantages
Throwaway accounts only — no real user data
Stripe test mode — no real transactions
AWS read-only IAM — zero real damage possible
